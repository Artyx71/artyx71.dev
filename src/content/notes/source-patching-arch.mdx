Applying a CSS change to the browser is the easy part. Writing it back to disk without triggering a cascade of unintended reloads is where the architecture matters.

## The naive approach and why it fails

Write the change to the file. The file watcher detects the change. The bundler re-processes the file. HMR kicks in and re-injects the stylesheet. The patch you just applied in the browser gets overwritten.

This loop makes the tool useless.

## Breaking the loop

LiveStyleSync uses a short-circuit mechanism: before writing to the file, it signals the WebSocket bridge to suppress the next HMR event for that specific file path. The bridge holds the suppression token for 200ms — long enough for the write + file watcher cycle, short enough to not suppress legitimate user edits.

```
1. Browser sends patch event  →  WS bridge  →  overlay applies patch
2. WS bridge records: suppress next HMR for path X
3. Source patcher writes to file
4. File watcher fires  →  bundler sends HMR event for path X
5. WS bridge sees suppression token  →  drops HMR event
6. Browser keeps patched state
```

## Edge cases

**Concurrent edits**: if the user edits the file in their editor while a patch is in flight, the suppression token may drop the legitimate HMR. Current approach: 200ms is short enough that this is unlikely in practice. A proper fix would version the suppress token against a file hash.

**Multiple patches in flight**: patches queue at the bridge, not the browser. Each patch gets its own suppression token.
